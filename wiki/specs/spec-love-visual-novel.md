# 恋爱 Galgame 视觉模式（spec）

> 状态：**方案**（2026-10-10，待实施）
> 日期：2026-10-10　|　关联：[恋爱独立模块](./spec-love-module.md) · [场景创作](./spec-scene-craft.md) · [3D 饭局](./spec-3d-table-culture.md)

## 一、背景与目标

用户方向：恋爱模块增加一个**可选的 Galgame 游戏模式**——有画面、有剧情、有选项的沉浸式恋爱剧情体验。**它不是替代**现有教练练习（briefing → 对话 → 复盘的证据式链路），而是恋爱模块里一个独立可选的入口：同一个语料库，换一种"玩游戏"的呈现。

定位一句话：**恋爱模块的「教练模式」（现状）与「游戏模式」（新增）双入口并存，共用语料与档案，游戏模式不产生也不伪造能力评估。**

## 二、现状基线（2026-10-10 核对）

| 资产 | 现状 | 对 Galgame 的价值 |
|---|---|---|
| 恋爱场景 | 60 个（8 个 loveTopic 各 2+，deep 系列 37 个带 simulationFacts + hidden 动机 + 双语 + 原创 source） | 现成的"剧情+角色+分支"素材 |
| 角色模型 | `characters[]`：id/name/personality/stance/**hidden**/hue；`opening` 开场 | galgame 立绘/台词/隐藏线的基础 |
| 视觉锚点 | 每角色带 `hue`；`AvatarFigure`（`data/avatars.tsx`）按 seed+hue 程序化生成 SVG 头像（发型/肤色/瞳/表情，无外部图片） | 立绘可扩展为**半身像**，同一套色板 |
| 剧情线数据模型 | `Scenario.series?: { id, name }`（`data/corpus/types.ts` L56-57）**已存在，尚无场景使用** | 多场景连续剧情（approach → define → …）直接落这个字段 |
| 进度 | `loveProficiency: Partial<Record<LoveTopicId, number>>`（跨场景 topic 级，`store/useApp.ts` L76/L311） | "好感度/关系线"的既有数据层，游戏模式只读展示 |
| 3D 引擎 | `features/dinner/` 完整 3D（cast/avatar/表情/镜头，WebView2 已验） | **备选**立绘来源；本期不依赖 |
| 对话链路 | `practice/[id]`：Briefing → Chat（流式、多回合、条件式后续、可失败）→ Debrief | 游戏模式的回合/分支逻辑复用同一 roleplay API |

## 三、产品形态

### 3.1 双入口

```
/love 页（现状：场景列表 → 点卡片 → /practice/[id] 教练练习）
  └── 新增「游戏模式」入口卡片
        ├── 选剧情线（series）：如「初见 → 暧昧 → 见家长」
        └── 进入 /love/play/<seriesId> → Galgame 界面
```

- 每个场景卡片保留现有"教练练习"入口；**新增一个**"剧情模式"入口（仅对带 `series` 的恋爱场景显示）。
- 游戏模式读完一条线后，可回看、可换线、可重玩；进度记设备端。

### 3.2 Galgame 界面构成

```
┌────────────────────────────────────────────┐
│  背景（场景化，按 contextType/hue 生成的  │
│  渐变+装饰，或后续换正式美术）              │
│        ┌────────────────────────┐          │
│        │  角色立绘（半身像，    │          │
│        │  由 AvatarFigure 扩展）│          │
│        └────────────────────────┘          │
│  ──────────────────────────────────────     │
│  [角色名] 台词（逐句/逐段浮现，双语）        │
│  ──────────────────────────────────────     │
│  [选项 A]  [选项 B]  [选项 C]               │
└────────────────────────────────────────────┘
```

- **台词**：逐句浮现（打字机/渐显），支持点按跳过。
- **选项**：关键决策点给 2-4 个选项；选项由现有 `objectives`/`success`/`failure` 的方向生成，**不是**无脑好感度选择——选错走失败线，选对走成功线，中间有部分成功。
- **立绘**：v1 用 `AvatarFigure` 扩展出半身 SVG（头肩 → 半身 + 简单姿势/表情变体，沿用 seed+hue 色板，零美术依赖）；表情按对话情绪切换（3-4 种：neutral/smile/tight/teary）。
- **背景**：v1 用 CSS 渐变 + 场景 icon 装饰（按 `scenarioTone`/`hue` 取色）；不引入图片资产。

### 3.3 剧情线（series）机制

- 现有 `Scenario.series` 字段承担剧情线归属；`series.id` + `series.name` 双语。
- **首批 1-2 条线**，每条 3-4 个场景，取自现有 deep 系列并按序编排，例如：
  - `love-arc-approach`：「摄影散步开场（approach-hobby-event）」→「再见面（approach 续）」→「暧昧落地（define 线）」。
- 跨场景**连续性**：`series` 场景共享角色 cast（同名 character id）；后一场景 `opening` 承接前一场景 `success/failure` 的结果（`simulationDirection` 已承载条件式后续的口径）。
- 线内进度：设备端记 `{ seriesId, completedScenes, lastResult }`，重玩清空重记。

## 四、架构与复用

### 4.1 数据层（零新增 schema）

| 复用 | 说明 |
|---|---|
| `Scenario` | 游戏模式**直接消费现有场景对象**，不新增类型；`series` 字段补上即可 |
| `simulationFacts` / `hidden` | 游戏模式的隐藏动机揭示条件沿用同一口径（具体问题才揭示，不提前吐露） |
| `loveProficiency` | 游戏模式完成场景**只读**展示 topic 热度，**不写**评估（见红线 2） |
| `source` | 每场景 source 已溯源，游戏模式沿用 |

### 4.2 对话链路

- **v1 简化**：游戏模式不接流式 LLM，用场景静态数据驱动（opening + 角色台词 + 选项分支），选项结果按 `success/failure` 方向给反馈句（双语，由场景数据派生）。
- **v2 增强**（后续）：接 `/api/roleplay` 流式让 NPC 即兴接话，选项仍是骨架；此时沿用现有流式/续段/可失败机制。
- 红线：游戏模式**也是练习**——选项判定不靠随机，失败/拒绝/让步/修复路径全部保留（见验收）。

### 4.3 视觉

- 立绘：`AvatarFigure` 扩展（`data/avatars.tsx` 新增半身变体，复用 `portraitFor`/色板/发型路径，不请求外部图片）。
- 背景：CSS 渐变 + 装饰，色板取自 `scenarioTone`/hue。
- 动画：Framer Motion（项目已有）做台词浮现、立绘切换、选项高亮。
- **3D 引擎为备选**：若产品想升级，后续可把 `features/dinner/` 的 avatar 渲染成 2D 立绘帧（本期不做，避免双管线维护）。

## 五、验收标准

### 5.1 结构（新增/改动后必跑）

- `pnpm lint` / `tsc` / `check-corpus` / `build` 全绿。
- 新增文件 ≤ 900 行/函数 ≤ 50 行，遵守现有组件分层。
- 所有新增文案进 `L(zh, en)` 双语对象。

### 5.2 剧情质量（沿用项目红线，**不是**只测标准答案）

每条剧情线实测验收**必须包含**：让步（NPC 偶尔松口）、拒绝（明确说不且不讨好）、反问（NPC 质疑用户）、玩笑（情绪调节不硬转弯）、修复（失误后留修复路径）、续聊（自然延续）。选项至少一条路径通往失败/拒绝，且失败后仍有退路——**杜绝固定回合换题、编造紧急事件、重复施压**。

### 5.3 隐藏动机（沿用 deep 口径）

- `hidden` 只对具体问题揭示（"你是不是已经先答应了你妈什么"），不提前吐露。
- 界面不显示"隐藏动机"标签；用户问对问题才在台词里自然浮出。

### 5.4 双红线

1. **NPC 不讨好用户**：游戏模式选项绝不出现"无脑加好感"的设计；阻力是护城河。验收：NPC 拒绝、质疑、保留都在。
2. **语料必须有 source**：新剧情线只重组现有场景（`series` 引用同一批 `source`），**不新增**无出处的剧情/角色/台词。若某线需要新场景，按 `spec-scene-craft.md` 流程创作并带 source。
3. **不引入账号/服务端存储**：线内进度记设备端（沿用 `localStorage`/`sessionStorage` 现有模式），可导出。
4. **不污染教练主链**：游戏模式完成场景**不写** `sessions`/`loveProficiency` 评估（避免"玩游戏刷能力"），`/progress` 与雷达不受影响。`/love` 教练入口保持原样。

## 六、实施步骤（分期）

### P1：视觉壳 + 单场景试玩（风险最低，先验证手感）

- [ ] `AvatarFigure` 半身立绘变体（表情 3-4 种）
- [ ] `/love/play/[scenarioId]` 单场景 Galgame 界面（背景/立绘/台词/选项）
- [ ] 选项结果按 success/failure 给反馈，接回场景列表
- [ ] 验收：5.2 剧情质量抽查 1 条 deep 场景

### P2：剧情线 + 设备端进度

- [ ] 首批 1-2 条 series（3-4 场景，复用现有场景，`series` 字段落地）
- [ ] `/love/play/[seriesId]` 线式入口 + 线内进度（设备端）
- [ ] 跨场景承接：后一场景 opening 反映前一场景结果
- [ ] 验收：完整跑通一条线，含拒绝/失败/修复路径

### P3：增强（可选，单独评审）

- [ ] 接 `/api/roleplay` 流式即兴
- [ ] 隐藏动机揭示动画
- [ ] 好感/信任度条（只读展示，不驱动评估）
- [ ] 3D 立绘帧升级评估

## 八、开放问题（实施前定）

1. **游戏模式是否计入"今日练习"统计**：建议**不计**（独立计数或忽略），避免与教练链路口径混淆——实施时在 P1 与用户确认。
2. **立绘风格**：SVG 头像扩展（零资产、一致性强）vs 引入 AI 生成立绘（视觉上限高、需资产管线与 source 溯源）：建议 P1 用 SVG，体验后再议。
3. **系列归属**：现有 60 个场景哪些进首批线（建议 approach/define 线先做，素材最足）；其余 6 个 topic 的线是否要补场景（走 spec-scene-craft 创作流程）。
