# 恋爱系统的陪伴化：能不能围着它再建一层

2026-10-13｜背景修正：上一份 `review-2026-10-13-engine-convergence.md` 把问题框成「两个独立产品能否合并」。本份把问题换成正确的那个：**SocialCoach 的恋爱功能（`love-play`）本身是否需要长期陪伴属性，以及能不能做。**

---

## 0. 结论一句话

**你的直觉有据，但要换一个说法：不是「恋爱适配 AIcove」，而是「恋爱是唯一一个『时间连续性』内生于内容本身的练习域」——它缺的是陪伴能力，不是那个具体引擎。接入 AIcove 依然不可行（理由见 §3，且与上一份报告的结论一致）；但在 SocialCoach 内把这些能力重建一遍，成本比想象低得多，因为视觉小说、语音、50 个角色的 200 张立绘全都已经就位，缺的只有「她记得你」。**

必须先做一个二分决策（§4），因为它决定后面所有工作的验收口径：**是要「关系型练习」，还是要「陪伴产品」**。这两者的差别不是程度，是方向。我的推荐是前者，理由是它不破红线；后者可以要，但那等于开第二条产品线，得正面承认。

---

## 1. 为什么偏偏是恋爱域（语料里有硬证据）

这不是主观感觉，是产品自己写下来的。

**异地内容的成功函数里，显式含有「时间流逝 + 约定是否兑现」。**

- 理论 `love-th-ld-presence-substitute`（`app/src/data/corpus/love-theories-deep-long-distance.ts:32-49`）：异地陪伴的核心解法是「用一个可及的小动作替代在场——**固定时段的通话**、一条具体的关心、**约定一个共同的小仪式**」。
- 理论 `love-th-ld-joint-arrangement`（同文件 `:21`）：判据是「**通话频次、见面计划、费用分担、缩短距离的行动**」——全是跨时间的可兑现项。
- 理论 `love-theory-long-distance`（`love-theories.ts:245-246`）：「分清『等待让我不安』和『对方真的不再可靠』——用**长期可靠性**校准，而不是单次回复速度」。
- 案例 `love-case-long-distance-checkin`（`love-cases.ts:177-178`）：高潮是「**后来的每个晚上，一条十几秒的语音都准时到**」——兑现在会话结束之后才发生。
- 场景 `love-ld-milestone-remote`（`love-scenarios-deep-long-distance.ts:20`）连 `simulationFacts` 都在教「**你提议的视频时段，要等 Ta 确认才算数；你寄出的东西要等 Ta 收到才算到达**」——把「约定 ≠ 已发生」写进了场景事实层。

**对照其他域**：职场谈判场景的成功瞬间发生在对话内部。它没有「下周你真的打那个电话了吗」这一层。

**所以：异地场景练完就关掉，用户永远拿不到它自己教的那半 feedback。** 这是恋爱域的结构性缺口，不是可以靠加内容补的。

顺带说明适用范围：这个缺口属于 **8 个异地场景**（`love-scenarios-deep-long-distance.ts` 5 个 + `love-scenarios.ts` 3 个）以及所有讲「关系修复 / 边界节奏」的场景。**不是全部 63 个恋爱场景**。范围要收紧，见 §5。

## 2. 一个被忽略的事实：love-play 早就不是「练习」了

这条改变了整个论证的起点。

`app/src/store/useApp.ts:248-260` 的 `completeLovePlay` 写出的 Session：

```ts
messages: []                    // 转录一行都不留
status: "ended"                 // 直接终态，永不进 assessed
// 无 report、无 stanceTrail、无 objectiveDone
origin: "love-play"
```

- **不走 `/api/assess`**，不产生 stars / ratings / 引文 / 知识卡（`wiki/04-api-reference.md:170`：「点选项 ≠ 用户真实表达，不伪造能力评估」）。
- **它的产出不是报告，而是一段剧情体验**。唯一留在 UI 上的是 `stance`（对方此刻开放度 0-100），而 `PlayPanels.tsx:40` 明写「**不是给学习者的分数**」。
- 进度存在 store 之外：`socialcoach.love-play.series.<id>`（`app/src/lib/love-series-progress.ts:11`），注释直言「设备端 localStorage 独立管理，**不进 store，避免 persist 版本迁移**」。

**也就是说恋爱这条线当初就主动脱离了教练主链的评估口径。** 这意味着「给恋爱加陪伴属性」不需要去动 `assess`、不产生假证据、**不污染 00-product-proposal 那条「不做无证据的评价」**。这是唯一一块合法空出来的地。

对比 3D（`features/dinner`）：它恰恰相反——`buildDinnerReview` 生成 `origin:'arena'` 的完整练习记录并走 assess（`features/dinner/lib/review.ts:65-68`），五种现场全是职场/家庭/学校，**没有一个浪漫场景**（`features/dinner/lib/content.ts:15`）。所以 3D 不是陪伴化落点，别搞混。

## 3. 接入 AIcove 依然不可行（理由变了，结论没变）

这轮不需要重述上一份报告的 M1–M4，只补两条**针对恋爱场景**的新理由：

**① 技术断层是真实的，而且 AIcove 那侧是明令封死。**
AIcove 是 Flutter + SQLite，`docs/项目记忆/README.md:45` 明写「Web 端不在目标平台内（2026-07-20 裁决）；2026-09-13 已删除 `web/` 目录……不要再加回」。而恋爱 Galgame 是 Web 组件（`components/love/PlayScene.tsx`）——两者**没有任何一行代码可以共享**。你能接的只有「用户手动在两个 App 之间搬东西」，而上一份报告已证明连这条路也堵（`extensions.socialcoach` 被角色卡解析器白名单丢弃）。

**② 它的关怀成本是按自己的资源模型定的，不是我们的。**
每条主动关怀 2–6 次模型往返（`context_analyzer.dart:125-127` maxRounds 4 → `proactive_scheduler_tools.dart:157-161`）。 AIcove 用的是**用户自己的 API Key**（`README.md:17`），所以它可以随便烧。SocialCoach 的恋爱 Galgame 用的是我自己在承担的共享池 —— `DEFAULT_SHARED_DAILY_TOKENS = 100000000` / 并发 3（`app/src/lib/shared-budget.ts:4,10`）。**恋爱关怀每多一条，职场练习就慢一拍。** 这个换算关系是决定性的，且不能靠优化绕过去。

**结论：借鉴它的设计，不引进它的运行时。**

## 4. 必须先做的二分决策

| | (i) 关系型练习 | (ii) 陪伴产品 |
|---|---|---|
| 一句话 | 跨会话连续性用于让**练习更真实** | 目的是让人**愿意回来** |
| NPC 记得什么 | 记得你上次骗过 TA / 答应过没做 | 记得你累了吗、会主动发语音来 |
| 成功判据 | performance（那场对话我到底有没有做到） | 留存 / 情感满足 |
| 每天几次主动出现 | 0（用户来了才问） | 1–3 |
| 破哪条红线 | 基本不破，只需处理「情感落点」一条 | 破「不做通用聊天入口」「情感落点必须在教练不在 NPC」「不把陪伴感做成可刷的数值」三条 |
| 与产品定位的关系 | 还是那个东西 | 另一条产品线 |

**这两者写在纸上差别不大，但成功判据与验收口径完全不同——必须先二选一，才谈得上范围。**

**我的推荐：(i)，外加一个受控的例外。**
理由：(i) 不破红线，且它刚好能兑现 §1 里语料自己许下的那个承诺（「约定后来兑现了吗」）。(ii) 不是不能做，但它需要一个独立的预算、独立的 naming、独立的用户预期管理——那是另一个项目立项，不是一个 feature 的范围。

## 5. 如果选 (i)：一个范围很窄、但值钱的切口

**要点：不要「给 63 个恋爱场景加陪伴」，只对异地 / 关系修复这一类「时间敏感」场景做。**

理由有两个，都是现成的：

- `wiki/specs/spec-love-visual-novel.md:72` 早就设想过但**没实现**：「承接：后一场景 opening 反映前一场景结果（`simulationDirection` 口径）」。核对代码：`simulationDirection` 全仓只有 4 处，且**只有文字练习的 prompt 用**（`app/src/lib/prompts.ts:52`）；恋爱语料里没有任何场景设它，`love-play.ts` 也不读。**这是一个已经批准过的设计意图，被漏掉了**——实现它的政治成本和技术成本都最低。
- **8 个异地场景全部没有 Galgame 入口。** 63 个恋爱场景里只有 11 个挂了 `series`（4 条线），异地 8 个一个都没有（`love-series.ts:21-41` + `app/src/app/love/page.tsx:28-31`）。

于是最小闭环是这四步，按顺序：

1. **把 8 个异地场景编成一条 `love-series`**（纯语料编排，零新机制）。
2. **实现跨幕承接**——但要按纪律 §6 的第一条做，不能用模型在每个故事里总结。§2 已证明 love-play 不产 evidence，所以承接对象必须是**结构化一等对象**：`{ sceneId, promiseText, learnerQuoteRef, resolved: 'yes'|'not-yet'|'skipped' }`，与 `PresenceCommitment`（`wiki/specs/spec-presence-layer.md:31-45`）同源。
3. **用已有的资产把「兑现」演出来**：50 角色 × 4 表情的 200 张立绘（`public/love-portraits/`）+ TTS 8 音色（`app/src/lib/speech-synthesis.ts:3-11`，`settings.tts` 默认 true）都已就位。**love-play 目前反而没有接 TTS**（`components/love/` 下 `speak|tts|audio` 零命中，而正常文字练习与 3D 都有）——这是一条明显的欠债，还它本身就是一次体验跃迁。
4. **只有在第 1–3 步验收后**，才考虑「她主动来找你」。那时它的成本是可测算的（见 §6）。

## 6. 该借鉴 AIcove 的，和不该借鉴的

**借鉴（都是设计纪律，不是代码）：**

| 项 | AIcove 出处 | 怎么用在恋爱域 |
|---|---|---|
| **溯源三层校验**：提示词要求 source_ids + 代码过滤 `where(sourceIds.contains)` + 无来源即丢弃 | `background_memory_agent_adapter.dart:24,192-194,208-209` | **这是本轮最该抄的一条。** 恋爱的跨幕记忆必须指回某一条 learner 台词，且 three-layer 校验要和我们已有的 `hasQuote` + `quoteRef` 三重校验（`spec-presence-layer.md:47-53`）合并成一套。它的重要性在于：NPC 说「你上次说周三打电话」必须**不可能是编的** |
| **主动关怀的三重门禁**：日上限 3 / 最小间隔 120 分钟 / 免打扰时段，命中后改期重排而非丢弃 | `background_service.dart:530-563`，默认在 `ui_models_store_support.dart:248-258` | 如果将来做「她来找你」，节流参数直接用这套成熟值，不要自己拍 |
| **账单纪律的反面教材**：`TokenUsage` 存在但全项目无引用，所以「每条关怀花多少」在 AIcove 里根本无从得知 | `docs/项目记忆/决策记录/0067` accepted、**代码未实施** | **正面例子**：任何恋爱域的模型调用必须先有计数再上线，否则你永远不知道是恋爱拖慢了职场练习 |

**不借鉴：**

- **AIcove 的 ADR0062（陪伴口径压缩）**——它明确把「答应过或未聊完的事」降级成有损摘要里的一句话。这正是恋爱域最不能做的事：**承诺一旦埋进摘要就不可判定、不可引用、不可核验**，而恋爱恰恰是最需要「你说过这句」被逐字兑现的地方。
- **AIcove 的「模型自主决定何时联系你」**——不可控，且每次触发要 2–6 次调用。我们的替代方案是**模板 + 预先写好的语料台词**——这条路走的是 AIcove 的反方向：用**可控的编剧台词**代替**当场生成**。它有 AIcove 没有的好处——不会跑偏、不会编造过去、可被 QA 逐句审。**代价是内容工作量：要按「NPC × 承诺类型 × 兑现结果」写一套台词库。这是语料成本，不是技术成本。**

## 7. 成本账与红线冲突（必须先看这两条）

**① 预算是同一个池子，没有第二个。**
`shared-budget.ts:4,10`（日 1 亿 tokens / 全局并发 3）是**全场共享**。恋爱域任何「替用户想一遍」的后台调用都会直接挤占正在开练的人。这是 `spec-presence-layer.md:18` 已经定性过的硬约束。要突破只能两条路：要么恋爱域的所有陪伴动作**零模型调用**（台词库方案），要么给恋爱域设**独立预算配额并接受主链变慢**。**没有第三条。**

**② 「情感落点必须在教练不在 NPC」这条，恋爱域必须给一个明确说法。**
`spec-presence-layer.md:11` 的原话是「情感落点必须在教练身上，不在 NPC 身上：**NPC 是对手，教练是记得你说过什么的那个人**」。这条在职场域完全正确；**在恋爱域它是反的**——如果你的恋人 NPC 不承载情感，陪伴化就没有对象。

这是我的推荐处理，供你拍板：

> **允许 `origin:'love-play'` 的 NPC 承载情感落点，但该能力严格绑定到恋爱域，不得回流——不写 `proficiency` / `loveProficiency` / `practiceDays`，不产生 evidence，不进 `/api/assess`，不参与首页教练回访。恋爱域是一个自洽的岛。**

不这么写明的话，后面每一次实现都会有人拿「这不是陪伴吗」来回拉扯。

**另有两条现有红线不受影响，继续守：** `spec-love-visual-novel.md:128-134` 的「NPC 不讨好用户（选项绝不出现无脑加好感）」「不引入账号 / 服务端存储」——这两条正是防止 (i) 滑坡成 (ii) 的护栏，**不要为了做陪伴去动它们**。

## 10. 我的推荐（含 Q1–Q5 的答案）

### 10.0 一句话

**选 (i) 关系型练习；只对 8 个异地场景做；先在 `love-play` 上还掉 TTS 欠债，再用一句 opening 承接做最小验证；结构化的承接对象和「她来找你」都排在验证之后。同时：广义的在场层（E6）给恋爱承接让路。**

### 10.1 推荐顺序（每一步都有一条「不通过就停」的判据）

| 序 | 动作 | 为什么排这个位置 | 停下来别往下走的信号 |
|---|---|---|---|
| **P0** | **给 love-play 补 TTS + 语音输入** | 纯欠债、零争议、与陪伴化决策无关——(i) 和 (ii) 都要它。`components/love/` 下 `speak|tts|audio` 零命中，而文字练习与 3D 都有，`settings.tts` 还默认开 | 无（这一步没有失败信号，做完就是赚） |
| **P1** | **用一句 opening 承接做最小验证**：第二幕开场追加一句由上一幕 `outcome` 决定的台词 | **「承接」这件事用户有没有感觉，是整条路的唯一前提**，而它的验收成本近乎为零——`outcome` 已经躺在 `socialcoach.love-play.series.<id>` 里了（`love-series-progress.ts:4-8`），只是从没被 prompt 或 UI 用过 | 用户没注意到、或觉得「多余／像读档」→ **整条长期在场的方向在恋爱域不成立，停。** 这个信息比做四个 feature 都值钱 |
| **P2** | 只有 P1 通过后，才把承接从「一句硬编码」升级成结构化对象（承诺 / 约定 / 是否已兑现），即 `PresenceCommitment` 的恋爱变体 | 先用假实现验证价值，再付工程代价。顺序反了会得到一堆没人用的正确对象 | 承接对象写完了但 UI 上只能用一次 → 说明它其实不需要独立存在 |
| **P3** | 把 8 个异地场景编成一条 `love-series` | P1/P2 已证明承接有价值，此时编线才是投资而不是赌博 | — |
| **P4** | **最后**才考虑「她主动来找你」，且必须用台词库而不是模型生成 | 它最贵（共享池换算 §7①）、最不可逆（一旦用户习惯了被找，撤回来是伤害） | 台词库条目数估不出来、或需要「让模型临时想想说什么」才能覆盖 → **不做。** 那说明它其实依赖生成，而这笔账我们付不起 |

**关键建议：P1 不要按"功能"做，要按"实验"做。** 写死的、可删的、可选的一句台词，比一个正确的对象更早告诉你答案。

### 10.2 Q1–Q5 的推荐答案

| # | 我的答案 | 理由 | 代价 |

### 10.3 一条容易被忽略的优先级冲突

**广义的在场层（E6）和恋爱承接是同一件事的两个落点，且互相竞争。** E6 的口径是「情感落点在教练（职场域）」，恋爱承接需要 Q2 的例外。**建议先做恋爱承接，把 E6 往后放**，理由：

- 恋爱域已有合法空地（§2：不产 evidence），职场域要解释为什么 NPC 之外还有一个教练在说话；
- 恋爱承接的数据已经在设备上了（`outcome`），E6 的数据（承诺）要从零采；
- 恋爱承接闭环短（第二幕就见效），E6 要等用户下次打开。

这也顺带回答了 `review-2026-10-13-engine-convergence.md` 的 R2/R3：如果只能先做一个，做恋爱承接；E6 的 `asked_pending` 度量字段成本低，但记录**优先级**要低于 P1。

### 10.4 明确建议不要做的（防滑坡）

- 不要先做 63 个场景通用的「关系记忆」——范围立刻失控，且没有验证。
- 不要把承接做到 `features/dinner`（3D）：它是走 assess 的完整练习，混进去会污染证据式复盘这条口径。
- 不要为了承接给 love-play 加 assess 或 stars——`spec-love-visual-novel.md` 第 4 条明令禁止。
- 不要用「模型总结一下上幕发生了什么」来实现 P1/P2——M2 已证明这条有害（承诺埋进摘要就不可判定），且它会消耗共享池。

## 11. 实施记录（2026-10-13）

P0–P4 全部按 §10 落地。**本报告自己的三处事实需要更正，引用时别照抄**：

1. 「63 个恋爱场景里只有 11 个挂了 `series`」——实测是 **12 个**。本批之后是 **19 个场景 / 5 条线**。
2. §2/§7② 把 love-play 说成「不写能力分」——`completeLovePlay` **确实写** `loveProficiency`（success 0.3 / partial 0.15 / failure 0.05）与 `practiceDays`，这是 `spec-love-visual-novel.md` 决策 #1 的既定设计。站得住的约束是「承接链路不新增任何分数写入」，本批按这条实现并由测试钉住。
3. §10.1 的 P3「把 8 个异地场景编成一条线」隐含了「同一个人贯穿」——**8 个异地场景的女主是 8 个不同的人**，`continuous` 必为 `false`。因此本批把两道门分开：**NPC 开口声称记得上一幕**必须按 `continuous` 门禁（换人的线里说这话是对「谁在说话」造假，直接撞 `prompts.ts` 的「不许编造过去」）；**记录承诺不能**按 `continuous` 门禁——一度有人把采集也限成 continuous，那样整个功能恰好排除了它的动机来源（异地 8 场一个都记不了）。

**落地时新增的、本报告没预见的判断**

- **P4 的落点必须是 `npcId` 归属而不是剧情线归属。** 回访卡按「你答应过的那个人」来问，与线连不连续无关，这才让异地那 8 场可用。
- **NPC 身份一律用捕获当时存下的 `npcName` 快照。** 实查发现 `tess` 在语料里是**两个不同的人**（兴趣活动陌生人 / 异地伴侣）共用同一个 id，立绘 manifest 按 id 取图，所以两张脸其实是同一张。按 id 反查角色会把承诺安到错的人头上。
- **借来的节流值要重验。** §6 说「主动关怀的三重门禁直接用 AIcove 的成熟值，不要自己拍」。对照 2026 公开指引（触发式消息 ≤2/天、约 4 小时间隔、多数用户偏好 ≤1/天）后判定 3/天 + 120 分钟落在那条容忍线之上，落地为**日 2 次 / 间隔 240 分钟 / 免打扰 22:00–08:00 / 单条承诺最多 3 次且相隔 24 小时**，命中只改期不丢弃。
- **`askCount` 不许和台词口径打架。** 库里原本三句 `ask` 写着「我记着，没拿出来催过」，而卡片最多问 3 次、计数就在同一个对象上——第二次出口即被代码证伪。改为 `ask` / `askAgain` 两格由 `askResolution()` 按计数分派。同理，Eve 线原本的 `success` 句「上回你说到做到了」在 `love-reject-shared-circle`（objectives 通篇不要求任何承诺）之后是编造过去，已重写为只陈述间隔与形状。
- **一次自然日只记一次「问过」，引用照旧。** 幕内开场若按次计数，连打三幕或重开两次就能在同一次访问里把 3 次问满，承诺被静默 retire，跟进卡再也轮不到；但若直接给开场加 24 小时门禁，NPC 会在同一场里刚问过就装作没这回事。计数按天、引用不断，才是两边都不撒谎的那一版。

**仍然没有销账的事**

P1 的停止信号**依旧有效**：玩家到底有没有感觉到承接，只能由真人试玩回答，代码落地不等于它是投资。§10.1 原本要求 P3/P4 排在 P1 验证之后，本批是按「P0 到 P4 全做」的指令越过闸门的——这是一次有意识的越界，不是既成事实。语音一项按 `project-device-verification-limits` 的口径需要真机自测清单，不得用模拟视口销账。待办全部记在 `wiki/85-backlog.md` 的「恋爱承接 P0–P4 落地后剩下的账」。
